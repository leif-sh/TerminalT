# TerminalT Rust 后端开发规范

## 1. 适用范围

本规范适用于 `src-tauri` 下所有新增或修改的 Rust 代码，包括 SSH、SFTP、隧道、凭据、设置、诊断、Tauri Command/Event、数据迁移和测试。

## 2. 架构边界

- Tauri command 只负责输入校验、状态查找、调用领域服务和稳定错误映射。
- SSH 协议、认证、PTY、SFTP 和隧道逻辑放在 Rust 服务层，不放入 React 或 command handler。
- 运行期资源由 Registry 持有；前端只持有不可猜测 ID，不暴露句柄、指针或底层 channel。
- Session、Operation、Transfer、Tunnel 等状态机必须有单一所有者，避免前后端各自推断状态。
- 高频数据使用有界 channel 和批处理；不得逐字节、逐字符跨 IPC。
- 数据模型和 IPC 字段变更需要向后迁移、序列化测试和前端类型同步。

## 3. 输入与错误

- 所有来自前端、网络和远端服务器的数据均视为不可信。
- 在边界校验长度、范围、枚举、路径、NUL、地址和标识符。
- 使用 `AppError` 和稳定错误码；用户消息简洁，技术详情脱敏且保留错误链。
- 不使用 `unwrap`、`expect` 或 panic 处理可恢复运行时错误。
- 不把底层库调试结构直接返回前端，先检查是否含秘密或过量远端数据。
- 错误码一经公开不得复用为不同语义。

## 4. 秘密与凭据

- 密码、验证码、私钥口令、代理密码和认证响应只保留在必要内存生命周期。
- 可保存秘密只能进入 `CredentialVault`，普通配置只保存引用。
- 使用 `zeroize`/`Zeroizing` 包装可控秘密；完成、失败、取消和超时后尽快释放。
- 日志、错误、事件、测试快照、导出和 panic 信息不得包含秘密。
- 私钥内容不复制到应用数据目录，不自动扫描用户 `.ssh` 目录。
- 远端认证提示不得被当作可信指令或日志模板。

## 5. SSH 安全

- 只支持 SSH-2，并优先使用维护中库的安全默认算法。
- 不为兼容性静默启用已知弱算法。
- 首次主机密钥必须确认；已知指纹变化必须默认阻断。
- 连接测试、正式连接、重连、SFTP、跳板和隧道使用一致主机校验策略。
- 多跳时每一跳独立校验主机密钥和认证。
- Agent 签名结果绑定具体认证上下文，不跨会话缓存。

## 6. 异步、取消与恢复

- 长操作必须接受显式取消；等待网络、用户响应和 channel 时使用 `select!` 或等价机制。
- channel 默认有界，明确满载行为和背压策略。
- 取消、超时、远端关闭和应用退出都必须释放 socket、SSH session、SFTP channel、监听器和文件句柄。
- 应用退出有界等待，不因单个任务永久阻塞。
- 关闭操作尽量幂等；迟到事件和旧 prompt 响应必须安全拒绝。
- 单个会话或任务失败不得导致其他独立任务退出。
- 失败恢复不得暗示恢复远端 Shell/进程状态；重连建立新会话。

## 7. 文件与路径安全

- 本地和远端路径在边界校验，不拼接成本地或远端 Shell 命令。
- 文件写入优先临时文件加原子替换，失败不得破坏既有目标。
- 递归遍历限制根路径、深度、数量和符号链接行为。
- 删除、覆盖、权限修改等危险动作由前端明确确认，后端仍校验目标合法性。
- 只清理当前任务创建且能证明所有权的临时文件。

## 8. 持久化与迁移

- 配置写入使用原子替换或事务。
- 每种持久化格式包含 schema 版本。
- 迁移单向、确定、可测试；失败时保留原始数据。
- 导入未来版本应明确拒绝，不静默丢字段。
- 为每个 schema 保留固定样例、旧版迁移和导入导出往返测试。

## 9. 测试要求

- 纯逻辑使用单元测试覆盖边界值、非法输入和状态转换。
- SSH/SFTP/隧道使用 loopback 集成测试覆盖真实协议行为。
- 并发代码覆盖取消竞态、迟到消息、重复关闭和应用退出。
- 安全路径覆盖秘密扫描、主机指纹变化、路径逃逸和资源限制。
- 新错误码至少有一个触发测试。
- 修复缺陷先增加可复现测试，再实施最小修复。
- 测试不得依赖公网或真实用户凭据。

## 10. 性能与可观测性

- 终端输出保持字节流，按受控大小和时间窗口批量发送。
- 避免在异步执行器线程上执行阻塞文件或网络操作。
- 对队列长度、批量大小和并发数设置上限。
- 日志记录阶段、稳定 ID、耗时、计数和错误码；不记录终端正文或秘密。
- 性能优化必须以基准或压力测试为依据，不删除安全校验换取速度。

## 11. 依赖与版本

- 新依赖前检查维护状态、许可证、安全记录、功能必要性和二进制体积。
- 优先使用现有依赖和标准库，不为简单逻辑新增 crate。
- 依赖升级必须运行完整 CI，并关注 MSRV、Windows 和协议兼容性。
- 完成功能或 bug 修复后按仓库规则递增应用版本并同步锁文件。
- 不手工修改 `Cargo.lock` 中解析出的依赖条目。

## 12. 代码审查清单

- [ ] 模块职责清晰，command handler 未承载协议实现。
- [ ] 输入有边界校验，错误码稳定且技术详情脱敏。
- [ ] 无可恢复路径上的 `unwrap`、`expect` 或 panic。
- [ ] 秘密不会进入日志、事件、持久化、导出或测试输出。
- [ ] 取消、超时、断网、远端关闭和退出均释放资源。
- [ ] channel 有界，状态和资源所有权明确。
- [ ] 主机密钥和算法安全策略未被削弱。
- [ ] 数据模型有迁移、兼容和往返测试。
- [ ] 新功能包含单元、集成、异常和恢复测试。
- [ ] 版本、文档、发布说明与本地 CI 已按仓库规则完成。
